## Flow จริงในโรงงาน (ระบบทำตามนี้แล้ว)
1. แอดมินกรอก `/confirmation` → **บันทึกเข้าระบบ** (เปิดแท็บระบบ · ไม่เปิดให้กดลิงก์ "กดเปิดหน้าระบบ") → **รับงานใหม่** (PDF ลูกค้าเซ็นแนบทีหลังได้) → งานต่อท้ายคิว
2. ทุกหน้าเรียง**ตามคิว** ไม่ใช่กำหนดส่ง · งานด่วน = แทรกคิว (ฝ่ายผลิต / ผู้บริหาร / เจ้าของ · ต้องมีเหตุผล) · เริ่มงานที่ไม่ใช่คิวแรกได้แต่ต้องมีเหตุผล
3. คนหน้างานใช้มือถือส่วนตัว: เปิดแอปเจอ **บอร์ด** → เลือกสถานี (เครื่องจำไว้) → หน้าคิวสถานี (เริ่ม → เสร็จ · พักงาน)
4. **พักงาน:** ใครก็แจ้งได้ · **"แก้แล้ว ทำต่อ" เฉพาะฝ่ายผลิต / ผู้บริหาร** (งานเย็บ = ฝ่ายผลิต "เย็บต่อ") · แอดมินเห็นป้าย "ติดปัญหา · รอผู้บริหารแก้"
5. **เวลามาตรฐาน:** การ์ดส้ม (ใกล้ครบ 80%) / แดง (เกิน) อัปเดตเองทุก 5 นาที · เกินแล้วต้องส่งรายงานปัญหาก่อนกดเสร็จ · ภาพรวมผู้บริหารขึ้น "เกินเวลามาตรฐาน"
6. แอดมินส่งออกได้ที่ พิมพ์ / รีด / ตัด / เย็บ / ปัก ที่ยังไม่เริ่ม · ส่งต่อบริษัทถัดไป · รับกลับ → สถานีถัดไป (งานแก้ → QC) · ระหว่างอยู่ข้างนอกโรงงานกดเริ่มไม่ได้
7. ยังบังคับเดิม: รีดฟิล์มรอได้รับฟิล์ม · QC ผ่านครบจำนวน · ข้ามสถานีไม่ได้ · ทุกการเปลี่ยนสถานะมี 1 แถวใน `events`

## รอเจ้าของตัดสิน / รอข้อมูล
1. **นับเวลามาตรฐาน:** `private.work_days` นับ 1 วัน = 24 ชม. (จันทร์–เสาร์ รวมกลางคืน) ไม่ใช่ 08:00–18:00 · เปลี่ยนต้องแก้ฐานข้อมูล + ตั้ง `sla_days` ทุกสถานี/ช่วงใหม่ · แนะนำหลังเปิดใช้
2. **CAP จักรต่องาน** (ทำหลังเปิดใช้ · รอใบเก็บข้อมูลจากหน้างาน `docs/ใบเก็บข้อมูล-จักรต่อตัวเลือก.pdf`):
   - **จักรผูกกับสเปกที่ลูกค้าสั่ง ไม่ใช่ชนิดสินค้า** · จักรของงาน = โครงพื้นฐาน + จักรของทุกสเปกในใบยืนยัน · ช่วงแรกฝ่ายผลิตเลือกจักรต่องานเอง
   - วันเย็บ = setup (5 นาที × จำนวนกระบวนการ ต่อชุด) + จำนวนตัว ÷ (ตัวต่อวันต่อชุด × จำนวนชุด) · **CAP** = ชุดน้อยสุดที่ทันนัด
   - จักรว่างเกิน CAP = จักรช่วย · งานใหม่ต้องใช้ → ระบบเสนอดึงคืน (งานที่เผื่อเวลามากสุดก่อน) → **ฝ่ายผลิตกดยืนยัน** (ไม่ดึงอัตโนมัติ · แยกบทบาทหัวหน้าทีหลัง)

## วิธีทำงาน (ทำทุกครั้ง)
1. ทุกงาน: branch `claude/…` จาก `origin/main` → PR → CI ผ่าน → **ถามเจ้าของ** → `gh pr merge <n> --merge`
2. ทดสอบ: `cd app && npm run lint && npm test && npm run build` · `cd supabase/tests && npm test` · บอกผลเป็นตัวเลข
3. **migration:** ชื่อหลัง `20261120070000` · ห้ามแก้ไฟล์เดิม · ฟังก์ชันที่ `create or replace` คัดลอกจากไฟล์ล่าสุดที่นิยามมัน · เพิ่มพารามิเตอร์ = `drop function` แล้วสร้างใหม่ + ให้สิทธิ์ `authenticated` ใหม่ · มีทดสอบทั้งผ่านและปฏิเสธ
4. **ลงฐานข้อมูลจริง:** `apply_migration` ถูกระบบสิทธิ์ปฏิเสธ → เจ้าของรันไฟล์ทั้งไฟล์ใน Supabase → SQL Editor ("ลงเองใน Supabase") → Claude ตรวจ `md5(replace(prosrc, chr(13), ''))` เทียบเนื้อ `$$…$$` ในไฟล์ (สคริปต์ Python ใน scratchpad · bash heredoc ยาวมักพัง) → `insert into supabase_migrations.schema_migrations (version, name) …` → อัปเดต memory prod-migration-state → แล้วค่อย merge (**ลงก่อน merge เสมอ** · Cloudflare deploy ทันทีที่ merge)
5. **ปรับค่าในฐานข้อมูลจริงชั่วคราว** (เช่น ย่อเวลามาตรฐานให้ AI ทดสอบ): จดค่าเดิมก่อน · เขียน memory เตือนคืนค่า · คืนทันทีที่ตรวจเสร็จ · ลบ memory
