## ส่วน A — แกนของระบบทดสอบ
1. **คำสั่งเดียว:** `node tools/qa-suite/run.mjs` แบบ
   - `--quick` (≤ 10 นาที · ใช้ก่อนเปิดทุก PR) · `--full` (ทุกส่วน · ข้อมูลเยอะ · ทุกขนาดจอ)
   - `--only <ส่วน>` · `--seed <เลข>` · `--days <n>` · `--out <โฟลเดอร์นอก repo>`
   - เปิดระบบจำลอง build ตรวจ bundle รันทุกส่วน แล้วปิดทุกอย่างเอง · ออกด้วย exit code ≠ 0 เมื่อมีข้อไม่ผ่าน
2. **ทำซ้ำได้ทุกครั้ง:** ทุกอย่างที่สุ่ม (ลำดับการกด · ข้อมูล · บัญชี) ใช้ seed เดียว · บันทึกทุกการกระทำเป็นบรรทัด (ใคร · ทำอะไร · ผล · เวลา) ลงไฟล์ · เมื่อล้ม ต้องมีคำสั่ง 1 บรรทัดที่รันซ้ำแล้วล้มที่จุดเดิม และ **ย่อขั้นตอนให้สั้นที่สุดที่ยังล้ม** (ตัดขั้นที่ไม่เกี่ยวออกทีละขั้น)
3. **รายงานอัตโนมัติ:** หลังรันได้ไฟล์ `report.md` + `report.json` (สรุปผ่าน/ไม่ผ่านทุกส่วน · ข้อที่ล้มพร้อมคำสั่งรันซ้ำ ขั้นตอนย่อ ภาพหน้าจอ log ของเบราว์เซอร์และหลังบ้าน) · ผลรอบก่อนกับรอบนี้เทียบกันได้ (ข้อที่เพิ่งล้ม / เพิ่งหาย)
4. **ขยายได้:** เพิ่มขั้นตอนใหม่ / ข้อตรวจใหม่ / หน้าใหม่ ด้วยไฟล์เดียวต่อเรื่อง · README อธิบายวิธีเพิ่มพร้อมตัวอย่าง · Claude ต้องใช้ต่อเองได้โดยไม่ต้องถาม

## ส่วน D — ตัวไล่หน้าจออัตโนมัติ
ทุกหน้า (`#/…`) × ทุกบทบาท × ขนาด **375 / 768 / 1440** × ทั้งไทยและพม่า (หน้าพนักงาน / QC) × สถานะข้อมูล (ว่าง / ปกติ / เยอะ / ผิดพลาดเพราะปิดหลังบ้าน) ตรวจอัตโนมัติ:
- หน้าไม่ล้นด้านข้าง (แยกให้ได้ว่าล้นจริงหรือแค่ระหว่างภาพเคลื่อนไหว) · ไม่เลื่อนไปเจอพื้นที่ว่างใต้แอป · ปุ่มหลัก ≥ 48 px · ตัวอักษรหลัก ≥ 16 px · ปุ่มที่กดไม่ได้มีเหตุผล
- ไม่มี `NaN` `undefined` `null` `Invalid Date` `[object` ข้อความอังกฤษหลุด (`Failed to fetch` ฯลฯ) · console ไม่มี error · ไม่มีคำขอเครือข่ายที่ล้มโดยไม่บอกผู้ใช้
- หน้าที่บทบาทไม่มีสิทธิ์ เปิดตรงๆ แล้วต้องไม่เห็นข้อมูล · หน้ามีสถานะ กำลังโหลด / ไม่มีข้อมูล / ผิดพลาด
- หน้าพนักงาน/QC โหมดพม่า: ไม่มีคำไทยตัวใหญ่ที่ยังไม่แปล
- ใช้คีย์บอร์ดอย่างเดียวในหน้าหลักได้ · เก็บภาพทุกจอไว้เทียบรอบถัดไป (ภาพเปลี่ยนเกินเกณฑ์ = แจ้งให้คนดู ไม่ใช่ล้ม)

## ส่วน E — สิทธิ์อัตโนมัติ
- ดึงรายชื่อฟังก์ชัน RPC ทั้งหมดจากฐาน (`pg_proc` ใน schema `public`) แทนการพิมพ์รายชื่อเอง · เรียกทุกตัวด้วย token ของทุกบทบาท (รวม anon · บัญชีปิด · staff ยังไม่จับคู่สถานี) เทียบกับตารางคำตอบ (เริ่มจาก `flow-r13-matrix.mjs` + `api-workflow.md`)
- **RPC ใหม่ที่ไม่อยู่ในตารางคำตอบ = ล้ม** (บังคับให้คนเขียนสิทธิ์ทุกครั้งที่เพิ่ม)
- เขียน/ลบตารางตรงผ่าน REST ทุกตารางด้วยทุกบทบาท ต้องไม่ได้ · อ่านตารางที่ไม่ควรเห็นต้องไม่ได้ · ขอลิงก์ไฟล์ของงานที่ไม่ควรเห็นต้องไม่ได้
- XSS (`<script>` `<img onerror>`) ในทุกช่องข้อความที่แสดงผลและพิมพ์

## ส่วน F — ใบยืนยันการผลิตแบบสุ่ม
- สุ่มกรอกฟอร์มทุกสินค้า (รวม 4 ใบงานบริการ) ทุกตัวเลือก รวมของใหม่: สีปกเมื่อเลือกปกสำเร็จ · ผ้าเพิ่ม จำนวน + หลา/ชิ้น · ไซซ์ "อื่นๆ" + แก้ชื่อไซซ์ · ชนิดปก · หลายแบบหลายรูป (ผูกรูปกับแบบ)
- ตรวจครบวงจร: ฟอร์มเตือนเมื่อควรเตือน · บันทึกเข้าระบบ → รับงาน → ข้อมูลในงาน (`spec`) ตรงกับที่กรอกทุกช่อง · แก้ใบหลังรับงาน → ครั้งที่แก้ + ช่องที่แก้ถูก · PDF ฉบับลูกค้าแสดง **เฉพาะ** ช่องที่อนุญาต (`CUSTOMER_FIELDS` ใน `production-confirmation.html`) และฉบับโรงงานครบทุกช่อง · การ์ด "แบบในงานนี้" ตรงกับตารางแบบ (รูปของแต่ละแบบ)
- กรอกผิดแบบคนจริง: จำนวน 0 / ติดลบ / ทศนิยม / ใหญ่มาก · อีโมจิ · วางจาก Excel · ปี พ.ศ. ในช่อง ค.ศ. · เลขที่ใบซ้ำกับงานที่รับแล้ว (ต้องได้ข้อความตาม PR 241)

## ส่วน G — พิสูจน์ว่าระบบทดสอบจับบั๊กได้จริง
ระบบทดสอบที่ดีต้องจับบั๊กที่เคยเกิดได้ · เลือก **อย่างน้อย 8 บั๊กที่เคยแก้ไปแล้ว** จาก `claude-bug-sweep.md` / รายงานรอบ 15–20 (เช่น กด Enter รัวเพิ่มวัตถุดิบซ้ำ = แก้ใน commit `70b02b1` · ใบแก้จาก 2 แท็บทับกัน · งานหลุดเข้าไลน์ก่อนเช็ควัตถุดิบ · ฯลฯ) แล้ว:
1. สร้าง worktree ชั่วคราวของ commit **ก่อนแก้** (`git worktree add --detach $env:TEMP\pp142-old <commit>` · ลบทิ้งหลังใช้ · ห้าม commit อะไรในนั้น)
2. รันระบบทดสอบกับรุ่นนั้น → ต้อง **ล้ม** ที่บั๊กนั้น · รันกับ main → ต้อง **ผ่าน**
3. ทำตารางในรายงาน: บั๊ก · commit ก่อนแก้ · ส่วนไหนจับได้ · ใช้เวลากี่นาที · ข้อที่จับไม่ได้ = อธิบายว่าทำไม และเพิ่มข้อตรวจจนจับได้
นอกจากนี้ ข้อตรวจในส่วน B ทุกข้อต้องมีทดสอบ "จับได้จริง" ตามที่เขียนไว้ท้ายส่วน B
