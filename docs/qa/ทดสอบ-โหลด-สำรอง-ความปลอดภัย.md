# ทดสอบโหลด · สำรอง/กู้ข้อมูล · ความปลอดภัย

ตรวจ 20 พ.ย. 2569 ค่ำ · ปิดช่องที่ชุดทดสอบเดิมยังไม่ครอบ (PGlite ต่อได้ 1 connection จึงจำลองหลายคนกดพร้อมกันไม่ได้)

## 1. โหลด / หลายคนกดพร้อมกัน

รัน `node tools/load-test/run.mjs` (ต้องเปิด Docker · สร้าง container ก่อน):

```bash
docker run -d --name pp142-load -e POSTGRES_HOST_AUTH_METHOD=trust postgres:15-alpine -c max_connections=200
node tools/load-test/run.mjs
docker rm -f pp142-load
```

Postgres 15 จริง · ลง migration ทุกไฟล์ · ทุกคำสั่งเป็น connection แยกผ่าน `psql` (บทบาท `authenticated` + RLS เหมือนฐานจริง)

เวลาต่อคำสั่ง ~330 ms ส่วนใหญ่คือเปิด `docker exec psql` ใหม่ทุกครั้ง ไม่ใช่เวลาในฐาน · ฐานจริงบน Supabase ช้ากว่านี้ตามเครือข่าย (ไม่ได้ทดสอบเครือข่ายจริง)

### 1.1 บั๊กที่พบและแก้ (`20261120250000_start_sewing_recheck`)
- **กดเริ่มเย็บชนกับกดเย็บเสร็จ (งานเดียวกัน) → ไปเริ่มสถานี QC แทน** และจ่ายจักรค้างไว้ให้งานที่อยู่ QC · `start_sewing` ตรวจว่าอยู่สถานีเย็บก่อนล็อกงาน แต่ไม่ตรวจซ้ำหลังล็อก (ฟังก์ชันจักรตัวอื่นตรวจซ้ำครบแล้ว) · แก้: ตรวจซ้ำหลัง `lock_job` → "สถานะงานเปลี่ยนไปแล้ว … กรุณาโหลดหน้าใหม่" · ทดสอบบังคับจังหวะ: ก่อนแก้ไม่ผ่าน (งานไปอยู่ `qc_pack|doing`) หลังแก้ผ่าน
- โหมดให้ระบบเลือกจักรเอง (`p_codes = null` · หน้าเว็บไม่ใช้) กดพร้อมกันได้ error อังกฤษ `duplicate key … machine_assignments_active_uq` 4/8 · แก้ด้วย advisory lock → 0

### 1.2 ข้อจำกัดที่รู้
- `start_in_queue` ไม่รับรหัสสถานี (ต่างจาก `finish_station`) · บัญชี staff ถูกจำกัดสถานีจึงไม่กระทบ · บัญชีฝ่ายผลิต/ผู้บริหารที่หน้าจอค้างนานแล้วกด "เริ่ม" ตอนงานเพิ่งย้ายสถานี อาจไปเริ่มสถานีถัดไป · โอกาสต่ำ (หน้าเว็บอัปเดต realtime) · แก้หลังเปิดใช้ได้

### 1.3 รันซ้ำบน Postgres 17 หลัง `20261128000000_sweep_fixes` (24 พ.ย.)
- `run.mjs` เดิมไม่ผ่านข้อ "เลือกจักรตัวเดียวกัน 8 คู่" (สำเร็จ 1/16 · "งานนี้ไม่ใช่คิวแรกแล้ว …") แล้วหยุดกลางทาง · ไม่ใช่บั๊ก: กฎคิวใหม่บังคับ `start_sewing` ด้วย · แก้สคริปต์ให้เรียก `note_queue_skip` ก่อน `start_sewing(p_codes)` เหมือนหน้าเว็บ
- หลังแก้ผ่าน 15/15: เลือกจักร 8/16 ไม่มีจักรซ้ำ · จำลองทั้งวัน 30/30 ใน 126 วินาที (431 คำสั่ง · ถูกปฏิเสธตามกฎ 101) ไม่มี deadlock · อ่านพร้อมกัน 1,200 คิวรี p95 4.6 ms

## 1A. ทดสอบจังหวะชนของล็อก (`tools/load-test/race.mjs`)

ตรวจล็อกที่เพิ่มใน `20261127000000` / `20261128000000` ซึ่ง PGlite ตรวจได้แค่ว่ามีอยู่ · ทุกรอบใช้ "ประตู" (advisory lock แบบ shared) ให้ทุกคำสั่งเริ่มพร้อมกันจริง · ข้อที่ต้องการจังหวะเฉพาะค้างธุรกรรมด้วย `pg_sleep` · ทุกข้อแยกชนิด error เหมือน `run.mjs` และไม่ผ่านถ้ามี deadlock / serialize / timeout / error อังกฤษ

```bash
docker run -d --pull never --name pp142-race -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17.11 -c max_connections=200
node tools/load-test/race.mjs          # RACE_ROUNDS=20 (ค่าเริ่ม) · RACE_ONLY=a,b,... เลือกข้อ · ใช้เวลา ~22 นาที
docker rm -f pp142-race
```

ผลบน `postgres:17.11` (24 พ.ย. 2569):

| ข้อ | กรณี | รอบ | ผล |
|---|---|---|---|
| a | `revise_job_spec` ชน `split_job` 2 ทาง (แบ่งงานแม่ + แบ่งส่วนที่แบ่ง) | 30 | ผ่าน · ทุกส่วนรวมส่วนที่เพิ่งแบ่งได้สเปก/กำหนดส่ง/ครั้งที่แก้ใหม่ · error 0 |
| b | `start_sewing` · `start_in_queue` · `set_job_machines` · `resume_sewing` แย่งจักรเข็มเดี่ยวตัวสุดท้าย | 20 | ผ่าน · ได้ 1 ทุกรอบ (ผู้ชนะ: เริ่มเย็บ 9 · เย็บต่อ 6 · เพิ่มจักร 5) · ไม่มีจักรซ้ำ · คนที่แพ้ได้ข้อความไทย (ไม่มี `duplicate key`) |
| c | `set_machine_status(broken)` ชนเริ่มเย็บ / เย็บต่อ / เพิ่มจักร / พักงาน | 20 | ผ่าน · ไม่มี deadlock · จักรเสียไม่ถูกจ่าย · งานที่กำลังเย็บมีจักรครบ |
| d | 6 คนกดเริ่มพร้อมกัน: ปัก `start_station` (ไม่มีเหตุผล) · ปัก `start_in_queue` (มีเหตุผล) · พิมพ์ 2 เครื่อง · เย็บ `start_sewing` | 20/20/10/10 | ผ่าน · ไม่มีเหตุผล = เริ่มได้เฉพาะลำดับต้นคิว ที่เหลือ "ไม่ใช่คิวแรก" · มีเหตุผล = เริ่มครบ · `queue_skip` ≤ 1 แถว/งาน `visit` ตรง · พิมพ์เริ่มได้ 2 พอดี |
| e | แทรกคิวช่องเดิม 2 คน + รับงาน 2 + แบ่งงาน 1 พร้อมกันจน `queue_renumber` ทำงาน | 32 | ผ่าน · จัดเลขใหม่ 4 ครั้ง · เลขคิวไม่ซ้ำ · งานไม่หาย · งานจบ/ยกเลิกคงเลขเดิม · ลำดับตรงกับที่แทรก/แบ่ง |
| e2 | แทรกคิว/แบ่งงานที่ต้องจัดเลขใหม่ ชนคนกดเริ่มงานนั้น | 6 บังคับ + 20 พร้อมกัน | รอบแรกไม่ผ่าน (deadlock · ข้อ 1A.1) · **หลังแก้ผ่าน** ไม่มี deadlock / error อังกฤษ ทั้งบังคับจังหวะและพร้อมกัน |

### 1A.1 บั๊ก: `queue_renumber` ล็อกทั้งตารางขณะถือแถวงาน → deadlock (แก้แล้ว)
- `move_job_ahead` / `split_job` ล็อกแถวงาน (`lock_job`) ก่อน แล้วเมื่อช่องคิวหมดเรียก `private.queue_renumber()` ซึ่ง `lock table public.jobs in exclusive mode` · ถ้าระหว่างนั้นมีอีกคนกดคำสั่งที่ `lock_job` งานเดียวกัน (เช่น `start_in_queue` งานที่ถูกแทรก / งานที่ถูกแทรกก่อน / งานที่กำลังแบ่ง) คนนั้นถือ RowShareLock ของตารางแล้วรอแถว → วนรอกัน → Postgres ตัดคนหนึ่งด้วย `ERROR: deadlock detected` (อังกฤษ · ธุรกรรมนั้นยกเลิก ข้อมูลไม่เสีย)
- ลำดับซ้ำได้: (1) ใช้ช่องก่อนงาน B จนห่าง < 2 (2) ธุรกรรม C ถือแถว B (`note_queue_skip(B)` ค้าง) (3) `move_job_ahead(J, B)` รอแถว B (4) `start_in_queue(J)` รอแถว J (5) C commit → `queue_renumber` รอ ExclusiveLock ที่ติด (4) · (4) รอ (3) → deadlock
- แก้แล้วใน `20261128000000_sweep_fixes.sql`: `move_job_ahead` / `split_job` ตรวจช่องคิวและเรียก `queue_renumber` หลัง advisory lock แต่ก่อน `lock_job` (เลขคิวเปลี่ยนได้เฉพาะคนที่ถือล็อกคิว จึงอ่านก่อนล็อกแถวได้) · หลังล็อกแถวถ้าช่องยังไม่พอ = แจ้ง "สถานะเปลี่ยน" แทนการจัดเลขขณะถือแถว · รัน `RACE_ONLY=e` ซ้ำบน Postgres 17.11: ผ่าน 5/5 ไม่มี deadlock
