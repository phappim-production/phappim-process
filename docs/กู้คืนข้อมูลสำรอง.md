## ข้อจำกัดของไฟล์สำรองตอนนี้ (สำคัญ)
1. **ไม่มีฟังก์ชันกฎใน schema `private`** (`pg_dump --schema=public`) · กู้ไฟล์สำรองอย่างเดียวแล้วกดปุ่มใดๆ ไม่ได้ → **ต้องสร้างโครงสร้างจาก `supabase/migrations/` ก่อน แล้วกู้เฉพาะข้อมูล** (ตามขั้นตอนข้างล่าง) · ข้อมูลไม่หาย เพราะ `private` ไม่มีตาราง
2. **ไม่มีบัญชีผู้ใช้ (`auth.users`)** · 17 ตารางอ้างผู้ใช้ด้วย UUID → ต้องสร้างผู้ใช้ใหม่ด้วย **UUID เดิม** (UUID อยู่ใน `profiles.id` ในไฟล์สำรอง) · ผู้ใช้ตั้งรหัสผ่านใหม่
3. **ไม่มีไฟล์ PDF ใบยืนยัน** (Storage bucket `confirmations`) · ตอนนี้ 7 ไฟล์ · หลังเปิดใช้จะเพิ่มทุกงาน → ต้องมีวิธีสำรองแยก
4. **สำรองสัปดาห์ละครั้ง** (อาทิตย์ 02:00) · ระบบพัง = ข้อมูลหายได้ถึง 7 วัน

**ควรแก้หลังเปิดใช้ (ใบสั่งงานแยก):** สำรองทุกวัน · เพิ่ม `auth.users` (id · email) ลงไฟล์สำรอง · ดาวน์โหลดไฟล์ใน bucket `confirmations` เก็บเป็น Artifact ด้วย

## ขั้นตอนกู้จริง (ระบบเดิมใช้ไม่ได้)
1. GitHub → Actions → `db-backup` → รันล่าสุดที่สำเร็จ → ดาวน์โหลด `pp142-db-backup` (ไฟล์ `.dump`)
2. สร้างโปรเจกต์ Supabase ใหม่ · รัน `supabase/migrations/*.sql` ตามลำดับชื่อไฟล์ใน SQL Editor
3. สร้างผู้ใช้ใหม่ใน Authentication ด้วย UUID เดิม (อ่านจาก `profiles` ในไฟล์สำรอง: `pg_restore -f - --data-only -t profiles <ไฟล์>`)
4. ล้างข้อมูลตั้งค่าเริ่มต้นที่ migrations ใส่ (`truncate` ทุกตารางใน `public`) แล้ว `pg_restore --data-only --disable-triggers --no-owner -d <connection string> <ไฟล์>`
5. อัปโหลด PDF กลับเข้า bucket `confirmations` (ถ้ามีสำรองแยก) · เปลี่ยน `VITE_SUPABASE_URL` / key ใน Cloudflare Pages แล้ว deploy ใหม่
6. ตรวจจำนวนแถวเทียบกับข้อ "ผล" ข้างบน · ล็อกอินแต่ละบทบาทแล้วเปิดงาน 1 งาน

## ลองกู้ซ้ำ (ทดสอบ · ไม่แตะระบบจริง)
```bash
docker run -d --name pp142-restore -e POSTGRES_PASSWORD=x -v <โฟลเดอร์ที่มีไฟล์ .dump>:/backup -v <repo>/supabase:/supabase postgres:17
docker exec pp142-restore sh /supabase/restore/restore.sh /backup/pp142-YYYYMMDD.dump
docker rm -f pp142-restore
```
ไฟล์ `.dump` มีข้อมูลลูกค้า · ลบออกจากเครื่องหลังทดสอบ · ห้าม commit
